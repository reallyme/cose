# COSE_Mac

The generated `mac_create` and `mac_verify` operations implement RFC 9052
sections 6.1 and 6.3. The `MAC` authentication structure contains the exact
protected bytes, explicit external AAD and full attached or detached payload.
It is distinct from `MAC0`. HMAC 256/64, 256/256, 384/384 and 512/512 require
explicit allowlisting. Key and tag widths follow the existing protected HMAC
profile. Verification reuses its reallyme-crypto constant-time boundary.

Recipient creation supports direct shared keys and A128KW/A192KW/A256KW,
including nested recipient distribution. A generated oneof distinguishes a
leaf key from a nested group. Wrapped MAC keys and intermediate wrapped KEKs
are generated by reallyme-crypto's secure random source. They are never
returned. Direct mode requires a sole recipient at its layer, empty protected
bytes, an algorithm in the unprotected map and an empty byte-string ciphertext.
That RFC direct form is distinct from the existing private ML-KEM profile's
nil form. AE key-wrap protected bytes must also be empty.

Verification follows a caller-authorized index path from the outer recipient
array to a leaf key. It checks the selected algorithms against a separate
allowlist, unwraps each layer and authenticates the MAC before returning any
payload or authenticated metadata. An unsupported algorithm on an unselected
recipient does not block a supported selected path. Unprotected recipient
identifiers are discovery data and are never reported as authenticated signer
identities. Key discovery and trust remain outside this format library.

Limits are 32 recipients in the complete tree, four recipient layers, 32 labels
and 16 KiB per header bucket, 64 KiB of AAD and 1 MiB per encoded message or
authentication structure. Sensitive generated owners and crypto key owners
wipe keys, plaintext, derived intermediates and failure-path scratch buffers.
Malformed structures, duplicate/conflicting headers, critical extensions,
wrong content mode, trailing data, invalid widths and unwrap/authentication
failures produce fixed schema reasons.

| Requirement | Focused native/WASM test |
| --- | --- |
| Independent HMAC 256/384/512 vectors, exact creation bytes | `mac_independent_hmac_vectors_match_creation_and_verification` |
| Independent HMAC/A128KW vector and unwrap failures | `mac_independent_wrapped_hmac_vector_and_invalid_wrap` |
| Payload, AAD, tag, key, malformed and trailing-input failures | `mac_tamper_payload_aad_tag_key_and_structure_fail_with_fixed_reasons` |
| Truncation, detached content, exact protected bytes and clearing | `mac_detached_truncated_and_protected_byte_ownership` |
| Multiple/nested recipients and every AES key-wrap width | `mac_multiple_and_nested_aes_wrap_recipients_use_explicit_paths` |
| Unsupported unselected recipients | `mac_unsupported_unselected_recipient_does_not_block_valid_path` |
| Direct-mode restrictions, malformed headers, tag widths and depth | `mac_rejects_mixed_direct_recipients_invalid_headers_tags_and_limits` |

Independent sources are the COSE working group's
[HMAC examples](https://github.com/cose-wg/Examples/tree/master/hmac-examples)
and `aes-wrap-examples/aes-wrap-128-03.json`. The HMAC-01 tag also appears in
[RFC 9338 appendix A.5.1](https://www.rfc-editor.org/rfc/rfc9338.html#appendix-A.5.1).
Creation with wrapped recipients intentionally differs between calls because
it generates fresh keys. Tests authenticate each transport's independent
output rather than requiring random outputs to repeat.

Other registered MAC and recipient algorithms are not implicitly enabled.
Missing AES-CBC-MAC, ECDH/KDF, RSA-transport and other primitive/provider
coverage remains a reallyme-crypto workstream, with fixed unsupported failures.
